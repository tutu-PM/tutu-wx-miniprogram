# 存量项目：新增功能与小改动

适用：已经有小程序在跑，要做改造。核心原则是**尊重既成事实**——现成的页面结构、现成的组件与变量、用户已经形成的习惯。

---

## 先分清三种改造，自由度不同

| 类型 | 用户会怎么说 | 允许动到什么程度 |
|---|---|---|
| **优化视觉** | "看着普通""提升质感""重新设计一下" | 可以重新决定**当初随手定的视觉默认值**（颜色、间距、圆角）；但品牌资产（logo、主色、识别性元素）保留 |
| **改流程** | "点太多了""这一步多余""保存后要能看见" | **只动路径，不动外观**。不走视觉方向探索 |
| **加新功能** | "加个 XX""能不能支持 YY" | **新功能长得像老功能**。沿用现有变量和组件，不另造一套 |

搞错的后果：该大改的不敢改，或者只是加个功能却把整个视觉推翻重来。

**判断钥匙**：用户那句话动的是**外观**还是**路径/功能**。说不清就先问一句。

---

## 三种都要做的三件事

### 1. 盘家底

动手前先看清单，写在回复里：

- 有哪些页面（读路由配置，别猜）
- 有哪些设计变量（颜色、字号、间距定义在哪）
- **有没有 `02视觉风格/design-spec.md`**：有就核对代码与规范是否一致（不一致以代码为准回填）；没有就按实际在用的值补一份，**只补不重写**（见 `design-spec.md`）
- 有哪些可复用组件
- 数据存在哪（本地存储 key / 接口 / 云）——只确认位置，不改

不盘就动手，结果通常是重复造轮子，或者改错地方。

### 2. 留基线截图

**改之前先截现状。** 两个用处：改完对比"到底变好没有"；改坏了知道原来什么样。

截不到（没有工具链）就明说"未留存基线截图"，别跳过去不提。

### 3. 从源头改

- 颜色不对 → 改变量，别挨个页面改按钮
- 间距不对 → 改间距档位，别写死数值
- 组件样式不对 → 改公共组件，别每处覆盖一遍

**判断标准**：这个改动，如果以后要再调一次，改一处还是改十处？改十处的做法就是打补丁。

## 新增功能：先写影响面，再决定出不出 HTML 稿

### 1. 先分级

| 级别 | 判据 | 走法 |
|---|---|---|
| **大** | 新增页面 / 新流程跨 ≥2 页 / 动到 ≥2 个现有页面的结构或信息层级 / 新字段要在多处展示 | 写影响面 → **出 HTML 视觉稿** → 写代码 |
| **中** | 只在一页里加一块内容、加一个入口、多展示一个字段 | 写影响面 → 直接写，做完截图看 |
| **小** | 改文案 / 按钮名 / 颜色字号间距 / 删点名元素 / 红框指定位置 | 直接改代码 |

**"加个功能"这四个字不代表大。** 用户说"加个导出按钮"是小，说"加个收藏夹"是大。区别只看一件事：**它有没有自己的页面、自己的流程。**

### 2. 写影响面（大和中必做，小可跳）

四行，写在回复里，不单独建文件：

| 行 | 写什么 | 怎么找 |
|---|---|---|
| 关联了哪些现有功能 | 点名具体功能，不写"相关模块" | 搜这条数据或这个词在哪几页出现过 |
| 在哪一屏出现 | 新入口放哪、旧入口动不动 | 读路由配置，看它该挂在哪个 tab 下 |
| 会改坏什么 | 共用组件、共用状态、既有排序或筛选 | 看要复用的组件被几个页面引着 |
| 要不要改共用件 | 改了就列出受影响的页面 | 搜组件名，数一下引用处 |

**四个必答的问题：**

1. **这条数据还有哪几处展示？** 加一个字段，往往首页汇总、列表、详情都要跟着改
2. **这个入口和谁抢位置？** 底部 tab 满了就只能在页内加，会挤掉现有内容
3. **改排序/筛选，哪几个列表一起变？** 共用一个查询函数时，改一处动三页
4. **这个状态加进去，老记录怎么办？** 老数据没有这个字段，展示会是空的

**影响面写不清就动手，等于赌它不会撞到别处。** 撞上时用户看到的是"你把原来的功能弄坏了"，而不是"新功能有点小问题"。

### 3. 出 HTML 稿（只有"大"才出）

只画两类屏：**新页面本身** + **被改动的现有页面**。不重画整个产品。

关键约束：**稿子里必须用项目现有的颜色和组件样式**，不要顺手美化。

存量项目出稿最容易犯的错，是把"加一个功能"做成"顺手改了个版"——用户看到的是产品被换了皮，而不是多了个功能。

画法和交付方式见 `html-prototype.md`。

### 4. 实现

1. **确认它属于哪一类**（新功能，不是视觉优化）
2. **盘家底**，找出可以复用的组件和变量
3. **找参照**：项目里哪个现有页面最像它？照那个写
4. **只做这一块**，不顺手重构别的页面
5. **验证**：新功能自己走通 + 按影响面清单逐条确认相邻页面没坏

**最容易犯的错**：新功能做出"另一个产品"的质感——因为它用了新的按钮样式、新的间距、新的卡片。发现这种情况，先回头用现有变量。

## 小改动的边界

**小改动一律不出 HTML 稿，直接改代码。** 稿子是给"需要拍板方向"的事用的；改一个按钮名字不需要拍板。

算小改动（直接改，不重走流程）：

- 改文案
- 调数量、调顺序
- 删指定元素
- 指定元素改成指定样式（"保存按钮改成绿色""这里间距大一点"）
- **截图 + 红框指定位置 + 参考图指定目标** —— 这同时点名了"改哪里"和"改成什么样"，是最明确的小改动

不算小改动（要走流程）：

- 只说"别扭""不好看""优化一下"，没点名改哪里
- 要给整个页面换风格
- 要整页照着参考图还原（走原型转小程序）
- 要加新页面、新流程（按"新增功能"分级处理）

改完的收尾：

- 只改文案 / 数量 / 复用现有样式 → 改完就交
- 改了颜色 / 间距 / 样式 → **看一眼改动处和相邻元素**，确认没把邻接布局挤坏

---

## 不要做的事

- 不因为"顺手"重构无关代码
- 不把"改一个按钮"做成"重构整个样式体系"
- 不在改造过程中替换技术栈或引入新库
- 不动业务逻辑（除非这一轮就是加功能）
