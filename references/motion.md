# 动效基线

这份只解决一个问题：**什么时候该动、动多久、用什么参数。**

**读法：默认值优先。** 下面给的是"不知道选什么时就用这个"。不要为了显得用心而加动效。

---

## 一、结论：只做三处

完全不动的界面像一张截图：按下没回应、切换没来路。所以新页面和改了操作流程的页面，**先把这三处做出来**：

1. **主操作的反馈** —— 按下立刻有回应，完成时交出结果（按钮陷下去再弹回、勾号画出来、数字滚到新值）
2. **一处状态切换的来路** —— 选中、展开、增删列表项时，让人看见东西从哪来、到哪去
3. **首次进入的一次出场** —— 主角先到，其余按阅读顺序跟上，**只在第一次进入时播放**

**这三处之外，全部不做。** 每多一个动效，都要能回答"它承担了反馈、引导、连续、品牌表达中的哪一项"——答不出来就是干扰。

### 先说一个前提：小程序的页面转场你改不了

页面跳转的动画由**系统控制**，开发者无法自定义（`wx.navigateTo` 没有可用的转场参数）。所以：

- **不要设计"页面切换动画"**，这件事在小程序里不存在
- 所有动效都发生在**页面内部**：按钮、列表、弹层、加载
- 想营造"从列表进详情"的连续感，只能靠**页面内部的内容衔接**（比如详情页顶部用和列表相同的图片和标题），不能靠转场

这一条和 Web 完全不同。oil-ui 里那套"整页转场三选一（遮罩/交叠/共享元素）"在小程序里**全部用不上**。

---

## 二、按钮点击：默认就这一套

这是最常问的。三层，从最省到最完整。

### 第一层：什么都不写（先用这个）

`view` 和 `button` 自带 `hover-class`：

```xml
<view class="btn btn--primary" hover-class="btn--pressed">保存</view>
```

```css
.btn--pressed {
  background-color: #D9633C;  /* 主色压深一档 */
}
```

零成本，够用。**大部分次要按钮到这里就够了。**

### 第二层：加一点按压感（推荐给主按钮）

```xml
<view
  class="btn btn--primary"
  hover-class="btn--pressed"
  hover-start-time="20"
  hover-stay-time="120"
  bindtap="onSubmit">
  保存
</view>
```

```css
.btn {
  transition: transform 120ms cubic-bezier(.4, 0, .2, 1),
              opacity 120ms cubic-bezier(.4, 0, .2, 1);
}
.btn--pressed {
  transform: scale(0.96);
  opacity: 0.9;
}
```

**参数为什么是这几个：**

| 参数 | 值 | 理由 |
|---|---|---|
| `scale` | **0.96–0.98** | 再小就"塌"，0.99 又看不出来 |
| `hover-start-time` | **20ms** | 手指按下几乎同时，慢了会觉得"没反应" |
| 回弹时长 | **120ms** | 超过 200ms 会觉得黏、拖沓 |

**两个不要：**

- **不要用 `button` 的默认 `button-hover`（灰底）** —— 那是微信的默认态，不是你的设计
- **不要只改透明度** —— 触屏上单靠透明度变化，用户几乎察觉不到，必须有位移或缩放

### 第三层：需要"确认真实完成"时

按钮触发的如果是提交、支付、保存，**动作状态比动画重要得多**：

```xml
<button
  class="btn btn--primary"
  loading="{{submitting}}"
  disabled="{{submitting}}"
  bindtap="onSubmit">
  {{submitting ? '提交中' : '提交'}}
</button>
```

**这条比任何动效都重要**：用户连点两次，提交两条数据，是真实事故。防连点不是动画问题，是正确性问题。

### 震动：谨慎，别当信息通道

```js
wx.vibrateShort({ type: 'light' })
```

- **只在"完成 / 失败 / 选中"用**，不用于普通点击
- iOS 三档（light/medium/heavy）都有；**部分安卓只支持 heavy/medium，light 可能没反应**
- 所以**不要靠震动传递任何信息**——它只是锦上添花，没反应也不影响使用

### 什么时候完全不要按压动效

- 列表项点击（高频，缩放会让长列表"抖"）
- tab 切换（系统已有反馈）
- 已经在滚动中的元素

**高频操作用最短的反馈，或者不给。** 动效的价值在低频的重要时刻，不在每一次点击。

## 三、时长与曲线：只要两档时长、两条曲线

### 时长

| 场景 | 时长 |
|---|---|
| 按下 / 松开 | **120ms** |
| 展开、收起、淡入淡出 | **200ms** |
| 半屏弹层、抽屉 | **280ms** |
| 状态切换的跟随元素（列表项移位） | **200–250ms** |
| 首次进入逐项出现 | 每项间隔 **40–60ms**，总长 **≤600ms** |

**规则：离开比进入快，约为进入的 60–70%。**

### 曲线（只留这三条，不现编）

```css
--ease-standard: cubic-bezier(.4, 0, .2, 1);  /* 通用：按下、展开 */
--ease-in:       cubic-bezier(0, 0, .2, 1);   /* 进入：淡入、出现 */
--ease-out:      cubic-bezier(.4, 0, 1, 1);   /* 离开：收起、消失 */
```

**不要用 `linear`** —— 匀速运动看起来像机器，不像实物。

**小程序没有 `linear()` 弹簧写法**（旧 WebView 不支持），oil-ui 里那套"按刚度阻尼数值积分生成弹簧曲线"到这里用不了。`cubic-bezier` 足够，不要为了"物理感"硬造。

## 四、状态切换怎么动（四条）

### 1. 从被点的地方出发

点"加入"，商品缩成一个点飞进购物袋，袋子上的数字跟着跳一下；删掉一行，它朝删除按钮的方向收走，下面的行补上来。

**不要**：从头到尾各动各的，按钮、列表、数字互不相干。

### 2. 一次切换朝一个方向

卡片往左滑，标题、序号、底色也往左换。**方向一乱，就成了几段互不相干的动画。**

打开和关闭互为逆过程——从右边进的，就从右边出。

### 3. 只变形状时不做交叉淡化

筛选、展开说明、切换视图，内容还是同一个东西，只是尺寸位置变了：**让外框直接变形，内容立即显示新状态**。

交叉淡化会让新旧两张尺寸不同的画面叠在一起，出现重影。**只有内容本身换了，才淡入淡出。**

### 4. 列表增删：三类分开处理

| 变化 | 怎么做 |
|---|---|
| 被移除的 | 淡出 + 朝移除方向收拢 |
| 新加入的 | 淡入 + 从下方轻微上移（8–16rpx） |
| 留下的 | 平滑滑到新位置 |

三者用同一种淡化节奏。**全都用同一个动作，列表就会整片闪烁。**

## 五、小程序特有的六个坑

这一节是这份文件最该看的部分——下面每一条，Web 上没有。

### 1. 没有 `:hover`

小程序是触屏，`:hover` 在真机上会"点完之后一直保持高亮"，非常难看。

**一律用 `hover-class`**，不用 `:hover`。

### 2. `wx:if` 会直接删掉节点

节点没了，**退场动画根本播不出来**——你写了 `v-if` 变化后的过渡，但元素已经不在页面上了。

两种解法：

- 要做退场：用 `hidden` 或 `opacity: 0` 控制，**保持节点存在**
- 不做退场：直接用 `wx:if`，简单粗暴，反而是对的

**判断**：退场动画只在"删除、收起一个明显的块"时才值得，其余情况直接删。

### 3. 长列表不要做逐项入场动画

首屏 10 条以上，每条错开 50ms，总长就超过 500ms——**用户会觉得小程序卡了**，低端安卓更明显。

**要做出场，最多做前 3–5 项**；列表超过 8 条，就整片淡入一次，不要逐项。

### 4. 只动 `transform` 和 `opacity`

小程序的渲染是 WebView，和浏览器一样：

| 可以动 | 一动就掉帧 |
|---|---|
| `transform`（位移、缩放） | `width` / `height` |
| `opacity` | `top` / `left` / `margin` |
| | `box-shadow` |
| | `filter` / `blur` |

低端安卓上，动 `height` 做展开动画是**最容易翻车**的一类。展开高度做动画时，用 `transform: scaleY()` 或改变父容器高度后内部元素用 `transform` 补偿。

### 5. 毛玻璃（`backdrop-filter`）安卓支持差

iOS 好用，安卓大量机型不生效或直接变成不透明块。

**改用半透明纯色**：`background: rgba(255,255,255,.92)`。视觉上差一点，但不会一半机型崩。

### 6. 原生组件上面做动画会穿透

`map` / `video` / `canvas` / `camera` / `live-player` 是原生组件，层级最高。在它们上面滑入一个弹层，**动画过程中会出现穿透、闪烁、遮不住**。

**只能用 `cover-view` 覆盖**，或者干脆避开——不要让弹层从原生组件上方划过。

## 六、什么时候不要动效

这条比"怎么做"更重要：

- **滚动列表里** —— 滚动时任何动画都会和滚动抢帧
- **tab 来回切换** —— 用户是快速来回点，动画只会拖慢
- **输入框聚焦** —— 键盘弹起本身已经是动画，再加会抖
- **用户连续快速操作** —— 动画必须能被打断，新动作从当前位置接着走，不跳回起点重播
- **首屏之外的内容** —— 用户看不到，白耗性能

**一句话：高频操作给最短反馈或不给；低频的重要时刻才做完整动画。**

---

## 七、看不见的结果要说出来

一次点击产生了看不见的副作用（保存成功、复制到剪贴板、发送给家人），**用一条短暂提示说出结果本身**：

```js
wx.showToast({ title: '已保存：番茄炒蛋', icon: 'none' })
```

不要说"操作成功"——要说"什么成功了"。

确认类的时刻（选中、完成），可以用一次小幅弹出，**只在状态第一次变化时播放，重复点击不重播**。

---

## 八、检查动效（交付前必做）

1. **快速连点 5 次** —— 有没有卡在中间态？有没有重影？按钮有没有重复提交？
2. **返回再进** —— 出场动画有没有重播？（应该只在首次播放）
3. **滑动一个长列表** —— 有没有动画在抢帧、掉帧？
4. **真机看一遍**（不是模拟器）—— 模拟器帧率高于低端安卓，动画卡不卡只有真机能看出来
5. **动画期间能不能操作** —— 动画播的时候点按钮，有没有响应？业务状态要立即更新，不等动画结束

**没在真机看过，不许说"动效流畅"。**

---

## 九、交付说明里怎么写

做了动效，交付时必须写清：

- 做了哪几处（对照"三处基本动效"）
- 每处的时长和曲线
- **哪些没做**，为什么没做
- 在真机上验过没有

**没验就写"未真机验证动效"。** 不要把"写了动画代码"说成"动效已验证"。
