# 原型转小程序

适用：已经有可点的原型（HTML 原型、设计稿、Figma 导出页），要落成小程序代码。

---

## 第一原则：原型是标准，不是源码

原型的作用是**告诉你"要长成这样"**，不是给你复制粘贴。

三不要：

1. **不用 `web-view` 或 iframe 把原型整页塞进去。** 那是个壳：里面还是原型的假按钮假数据，接不上项目的状态和存储，用户点不动。
2. **不把原型的 CSS / JS 整段搬进工程。** 原型是"一个文件、全局样式、随手写的脚本"，工程有组件、变量、目录结构。搬进去等于塞一套野路子，以后改一处要改两处。
3. **不引入功能重复的第二个组件库。** 原型的样子用现有组件调出来，不需要再装一套。

三要：

- 用项目已有的组件
- 用项目已有的样式变量
- 用项目已有的组件库

**视觉还原用并排核对**：将小程序页面与已确认的稿件同宽比较。视觉对齐不等于验收完成，关键交互仍须在真机走通（见 `verify.md`）。

"对得上"不是感觉，有量化标准：**源头和结构必须一样，像素差 ≤2rpx，允许差异只有六类**。七条硬约束、差异白名单、八个量测点、交付要写的三行，全在 `consistency.md`。**别对用户承诺"像素级还原"**——那句话不成立，说清楚"哪层能一致、哪层只能近"更可信。

---

## 第二原则：Web → 小程序，这些必须换

原型几乎都是按 Web 写的。照抄会崩在这几处：

| 原型里 | 小程序里 | 为什么 |
|---|---|---|
| `px` | `rpx`（750 设计稿基准） | 要等比适配所有机型 |
| `div` / `span` / `p` | `view` / `text` | 小程序没有这些标签；`text` 内部才可选文字 |
| 页面整体滚动 | `scroll-view` | 长列表靠页面滚会卡；需要固定头部时更必须用 |
| `:hover` | `hover-class` / `:active` | 手机没有悬停 |
| 自己画的 tabbar | 原生 `tabBar` 配置 | 自己画的要处理选中态、图标、页面切换，还得处理返回 |
| 自己画的顶部导航 | `navigationBarTitleText` 或 `navigation-bar` | 原生导航栏还带胶囊按钮，自己画要避让 |
| `position: fixed` 悬浮元素 | 注意安全区，底部要留 `env(safe-area-inset-bottom)` | iPhone 底部横条会压住 |
| CSS 动画随便加 | 轻量、优先 `transform` / `opacity` | 低端安卓掉帧 |
| 任意网络字体 | 系统字体 | 小程序不能任意加载字体，包体积也受限 |
| `z-index` 随便叠 | 注意原生组件层级 | `map` / `video` / `canvas` / `camera` 永远在最上层 |

### 换算参考

- 750 设计稿：`1px`（设计稿）= `1rpx`
- 375 设计稿（@2x）：设计稿上的 `2px` = `1rpx`；或直接 `px × 2 = rpx`
- 最小点按区：**88rpx × 88rpx**（约 44pt），比 Web 的 44px 更宽裕，因为手指比鼠标粗

## 第三原则之前：原型不是规范，先收敛一次

原型通常是一页一个文件、随手写的样式。**同一个按钮在三个页面可能是三种圆角，五种近似的主色。** 逐页照抄，等于把混乱搬进工程。

所以先做一次收敛，产出 `02视觉风格/design.md`（模板见 `design.md`）：

1. **抽出原型里实际在用的值**：把所有颜色、字号、圆角数一遍，按出现次数排序
2. **合并同类**：取出现最多的那个当基准，把近似值（差 2–3 个色阶、差 4rpx 的圆角）归到同一档
3. **补齐原型没画的东西**：tab 图标两态、按钮的按下与禁用态、空/加载/出错三种状态——原型通常只有"成功态"
4. **原型与规范冲突时以原型为主**（它是用户点头过的东西），但把偏离的页面列出来，问一句"这些要不要统一"

收敛之后，页面按规范写，不再逐页照抄原型里的字面值。

---

## 第三原则：先拆结构，再写代码

拿到原型不要直接开始写 WXML。先做一遍拆解，写在回复里（不建文件）：

1. **页面清单**：原型里几屏，对应小程序几个页面，哪些是 tab、哪些是二级页
2. **共用部分**：反复出现的卡片、列表项、空状态 → 应该是同一个自定义组件
3. **状态清单**：每屏的空 / 加载 / 出错 / 成功分别长什么样（原型通常只画了"成功"）
4. **交互清单**：点哪里去哪、返回回到哪、下拉刷不刷新
5. **平台替换项**：上表里哪几条会命中

第 3 项最容易被漏。原型若只画了理想状态，先说明其余状态及跳转、返回行为，让用户确认未定项后再开发。

---

## 第四原则：一屏一屏对齐，不要一次全转

按"闭环最关键的一屏 → 走通 → 下一屏"的顺序做，每做完一屏就和原型并排核对一次。

**第一屏就是样板页**：用真代码写出来、模拟器截图、关键屏再上真机，三张图（用户的原型 / 模拟器 / 真机）并排给用户看。确认后再铺后面的页面——后面几页都是这一页的组件和规范在重复。

**已有原型和交互都已确认时，不再额外做 HTML。** 只补缺失状态和平台替换项；仅当用户明确要求 HTML 或有具体交互需要验证时，才对相应页面、动作和状态做最小范围的原型。

一次性把 8 屏全转完再核对，改起来是灾难——因为组件和变量都在变，前面写的全要跟着改。

---

## 原型本身就是截图的特殊情况

如果用户给的只是一张**静态截图**（不是可点原型），也走这条，但要注意：

- 截图里看不到的状态（空、加载、出错）先查已确认的交互说明；仍不清楚就提出方案请用户确认，不能装作截图里有
- 截图是等高缩放还是等比裁切，会影响信息密度，要按真机 750 宽重新算
- 截图里的字体多半拿不到，用系统字体近似，并在交付说明里讲清

- 并排核对的截图在哪
