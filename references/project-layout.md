# 项目目录与 git

这个 skill 产出的东西不能散在工程里。**一个产品一个总文件夹，四类产出一眼能找到。**

---

## 一、总文件夹怎么命名

| 情况 | 命名 | 例 |
|---|---|---|
| 有产品名 | 直接用 | `备忘录小程序/`、`家庭菜谱/` |
| 没定名字 | `小程序-当天日期` | `小程序-2026-11-19/` |
| 只有一个模糊方向（"做个记账的"） | 先按方向起个短名，后面能改一次 | `记账小程序/` |

三条规矩：

- **名字要能当产品名念出来，≤6 字。** 「用来记录工作灵感的小工具」不是名字
- **不改名。** 改名等于所有文档里的路径全要改；确实要改，一次性替换并检查
- **放在用户的工作目录根下**，不要塞进某个 `src/` 或 `docs/` 里；多个小程序不要混在一个目录

---

## 二、目录结构

```text
备忘录小程序/
├── 01需求文档/
│   └── prd.md
├── 02视觉风格/
│   ├── design-spec.md
│   ├── 原型/
│   │   ├── index.html
│   │   └── preview.png
│   └── 素材/
│       ├── tabbar/
│       ├── 插画/
│       └── 空状态/
└── 03代码/
    ├── package.json
    ├── src/
    └── ...
```

`01 / 02 / 03` 是**排序前缀，不是版本号**。永远不会有 04——新增产物往现有三档里归，不要一路加序号。

| 目录 | 放什么 | 不放什么 |
|---|---|---|
| `01需求文档/` | `prd.md`（一份，含定位、页面清单、功能、四态、兜底） | 设计稿、截图、会议记录、竞品链接堆 |
| `02视觉风格/` | `design-spec.md`（八节，唯一取值来源） | 代码、构建产物 |
| `02视觉风格/原型/` | `index.html` 视觉稿、渲染截图 | 真实业务代码、依赖 |
| `02视觉风格/素材/` | 所有图片、icon、插画、生图产物、空状态图 | 代码里临时生成的缓存图 |
| `03代码/` | 小程序工程本体，能独立 `npm i && build` | 文档、原型、素材原件 |

**素材按用途分一层子目录**（`tabbar/` `插画/` `空状态/`），不要全部平铺在一个文件夹里。

---

## 三、素材与代码的关系（最容易搞错）

`02视觉风格/素材/` 是**素材库，唯一来源**；`03代码` 里的 static / assets 是**运行时副本**。

```text
02视觉风格/素材/tabbar/inbox-normal.png   ← 原件，改动从这里开始
                ↓ 复制
03代码/src/static/tabbar/inbox-normal.png ← 副本，构建时打包进去
```

四条规矩：

1. **新素材先进素材库**，再从素材库复制进代码，不要反过来
2. **改素材改素材库那份**，改完覆盖代码里的副本；直接改代码里那份，下次一覆盖就丢
3. **命名 `用途-状态.png`**，小写英文加连字符：`inbox-normal.png` / `inbox-active.png`；不用中文名、不用空格
4. **格式**：不透明用 JPG，需要透明用 PNG。**不用 WebP**——iOS 真机上 `image` 组件显示不稳定，开发者工具正常、真机白图

素材库和代码副本对不上时，以素材库为准，把副本覆盖一次。

## 四、git：开工第一件事就查

### 检测

```bash
git --version                    # 有没有装
git rev-parse --show-toplevel    # 当前目录是不是已经在某个仓库里
```

**任何项目开工都先跑这两条**，不等要提交时才发现。第二条经常被漏：项目目录往往已经在某个大仓库（工作区、父目录）里面了，这时候再 `git init` 会造出嵌套仓库，把 `git status` 搞乱。

### 四种结果，四种处理

| 检测结果 | 怎么做 |
|---|---|
| **没装 git** | 问一次要不要装：给官方下载页，**由用户自己装**；不装就继续，交付说明写"无版本回退" |
| **装了，且当前目录已在某个仓库里** | 先告诉用户"这个目录已经在 `X` 仓库里了"，再给两个选择：**跟着现有仓库走**（推荐，直接提交，简单）/ **单独建一个**（会嵌套，需要处理忽略规则，不推荐） |
| **装了，且项目目录自己就是仓库根** | 已经在版本控制下，问一次要不要做首次提交 |
| **装了，但不在任何仓库里** | 等要开始写代码时问一次：要不要给这个项目建 git 仓库 |

### 有 git、可以建仓库时

**不要立刻建**，等要开始写代码时问一次：

> 要不要给这个项目建一个 git 仓库？建了以后每次改完都能看差异、能回退。

- **要** → `git init`，写好 `.gitignore`，做一次首次提交（文档 + 原型 + 素材 + 代码）
- **不要** → 记下来，同一项目后面不再问

### 没装 git 时

问一次：

> 这台机器上没检测到 git。要不要装一个？装了以后改动可以看差异、能回退；不装也能继续开发，只是没有版本记录。

- **要装** → 把官方下载页给用户（`https://git-scm.com/downloads`），**由用户自己装完并确认，AI 不代装、不代跑安装程序**
- **不装** → 继续开发，交付说明里写一句"本项目无版本控制，改动不可回退"

### `.gitignore` 模板

```text
node_modules/
dist/
unpackage/
.chrome-profile/
*.log
.DS_Store
```

### 三条规矩

1. **同一个项目只问一次。** 问过答复了就记进 memory 或 prd 备注，不再打扰
2. **首次提交要含文档和原型**，不只是代码——出问题时能回退到"视觉定稿那一刻"
3. **没有 git 不影响开工**，只降级到"不能回退"，不要因此卡住用户

## 五、已有项目怎么迁移

1. **先建新目录，再移动，不要复制**（复制会留下两份，以后必然改错那份）
2. **顺序：文档 → 原型 → 素材 → 代码。** 代码最后动，因为构建配置里的相对路径可能要跟着改
3. **迁完立刻验证两件事**：原型能在新路径打开；代码能编译
4. **旧目录空了就删**；有残留先列给用户，不自己清理
5. **迁完更新文档里的路径**，`prd.md` / `design-spec.md` 里引用截图、原型的地方最容易漏

---

## 六、什么时候不建这套

| 情况 | 做不做 |
|---|---|
| 只改已有项目的文案、间距、一个按钮 | 不建，直接改 |
| 纯咨询、竞品分析、只答疑 | 不建 |
| 一次性验证脚本 | 不建 |
| 从 0 做一个新小程序 | **必须建** |
| 给已有项目加一个较大功能 | 不新建总目录，产物按现有三档归位 |

---

## 七、交付时提一句

交付说明里写一行目录现状，用户才知道东西在哪：

```text
目录：备忘录小程序/（01需求文档 / 02视觉风格：风格规范+原型+素材 / 03代码）
git：已初始化，首次提交含文档与原型；node_modules 与 dist 已忽略
```
