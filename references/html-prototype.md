# HTML 视觉稿：写代码之前先看一眼

适用：从 0 开发第一屏之前、新增一个较大的功能之前、改动波及多页之前。

一句话：**先用一个 HTML 文件把"长什么样"摆出来给用户看，点头了再写小程序代码。**

---

## 一、为什么要有这一层

跳过它直接写代码，等于**用代码做设计**。代价是三处：

- 改一个间距要动编译、跑模拟器、截图，一轮十分钟
- 结构不对时，改的不是一个 div，是三个页面的 WXML 和一套组件
- 用户看到的永远是"已经写死的版本"，说"不对"时你要回滚代码，而不是删一行样式

HTML 稿把这个循环压缩到"改一个数字、刷新、看"。**它的唯一目的是让用户早一点说"不对"。**

---

## 二、什么时候必须先出

满足任意一条就出：

| 情况 | 为什么 |
|---|---|
| **从 0 开发，第一次落页面** | 页面结构和信息层级还没人看过 |
| **新增一个页面** | 新页面要塞进现有结构，位置和入口得先摆一次 |
| **新增流程跨 2 个以上页面** | 流程一长，改一处会牵动前后页 |
| **会改动 2 个以上现有页面的结构或信息层级** | 影响面大，改错要回滚多处 |
| **引入新字段/新状态，且要在多处展示** | 字段铺开后改名字要改一片 |
| **要换版式、重排信息层级**（"看着普通""重新设计一下"） | 这是方向问题，不是调数值 |
| **用户说不清要什么**，只能说"你看着办" | 用一版可视稿把分歧逼出来，比反复追问快 |

## 三、什么时候不用出（直接改代码）

| 情况 | 说明 |
|---|---|
| 改文案、按钮名字、提示语 | 纯文字替换 |
| 改颜色 / 字号 / 间距的取值，不动结构 | 换变量 |
| 删掉已经点名的元素 | "把这一行去掉" |
| 截图 + 红框指定位置和改法 | 改哪里、改成什么样都明确了 |
| 纯逻辑 / 数据修正，视觉不变 | 没有视觉决策 |
| 加一个按钮、一个入口，位置明确 | 结构没变 |

**判断钥匙：这次改动有没有"新增或移动界面上的一块内容"？**

没有 → 直接改。有 → 看出不出 HTML。

**拿不准时按"小"处理**：先直接改一版给用户看，他说"不是这个意思"再升级到 HTML 稿。
反过来做（把改文案也做成 HTML 稿）是在浪费用户的确认时间——而且会让他觉得你在拖。

---

## 四、怎么出（七条硬规矩）

1. **一个 HTML 文件，双击能打开**
   放 `02视觉风格/原型/index.html`。不引 CDN、不装依赖、不需要构建、不需要起服务。
2. **按 375 × 812 的手机屏画**
   设计规范用 750 基准，所以 **1rpx = 0.5px**：`40rpx → 20px`、`28rpx → 14px`、`12rpx → 6px`。
3. **多屏并排，不做页签切换**
   一屏一页横着摆开，用户一眼看完整个产品。每屏下方写一行小字：这是哪一页、这块在验什么。
   做成点击切换，用户就得一屏一屏点，反而慢，也看不出页面之间的关系。
4. **只用 design-spec 里的 token**
   CSS 变量名与规范同名：`--c-primary`、`--c-text-2`、`--fs-body`、`--sp3`、`--r-md`。
   **不要在 HTML 里临时发明颜色。** 原型里多一个色值，代码里就多一个要清理的东西。
5. **四态一起摆**
   空 / 加载 / 出错 / 成功。只画成功态，等于没验——而空态和出错态才是用户最先碰到的东西。
6. **不写业务逻辑**
   没有跳转、没有数据读写、没有校验。选中态用静态 class 表达即可。
   它是一张会呼吸的图，不是一个能用的应用。
7. **手机外框只是外壳**
   状态栏、胶囊按钮、tabBar 用简化图形表示即可，不用像素级仿 iOS。省下的时间用在版式上。

### 最小骨架

```html
<!DOCTYPE html>

<head>
```

## 五、出到什么程度算够

**够：**

- 主流程上的每一屏都有
- 关键页的空 / 加载 / 出错 / 成功都有
- 至少一屏展示"文字最多的情况"（长文案、两行截断、换行对齐）
- 底部 tab 的选中态至少出现一次
- 每屏都能在 812 高度内看到主要动作（放不下就是结构问题，暴露在这里比暴露在代码里便宜）
- **文案全部用真话写**，按 `copywriting.md` 的语气（说人话、可以带点贫）。稿子里的语气定下来，代码里才会是这个语气

**不必：**

- 全套页面——只做这轮要拍板的
- 动效演示——**不是漏了，是故意不做**：稿子的交付形式是静态截图，演了也看不见；而且 HTML 能做的小程序不一定能做（`wx:if` 删节点、原生组件上层穿透、页面转场由系统控制），在稿子里演出来等于给你一个做不到的预期。动效看 `design-spec.md` 第九节的取值，在模拟器里验
- 多机型的响应式
- 真实数据——用像真的假数据，不要 `测试1 测试2`
- 占位文案——`请输入内容` `暂无数据` `Lorem` `示例文字` 一个都不要，这几个字一旦进稿子，就会原样进代码

## 六、怎么交付

**用预览打开给用户看，不要只发截图。** 他能自己缩放、能看清间距。

同时说清三件事：

1. 这一版包含哪几屏，分别验什么
2. **想请他拍板的三处决定**（不要笼统问"这样可以吗"）
3. 确认之后下一步做什么

示范：

> 重点看三个地方：类型用色点还是色块、正文两行截断够不够、详情页要不要保留底部 tab。

**不要问"这样可以吗"。** 没有焦点的问题，用户只能回"还行"，你就失去了这次确认的价值。

---

## 七、确认之后

1. 用户提了修改 → **先改 HTML 稿**，再让他看一次。不要跳过稿子直接改代码。
2. 定稿的稿子留在 `02视觉风格/原型/` 里，当视觉参照，不要删。
3. 写代码时对照着写，**不搬 CSS**（见 `prototype-to-code.md`），并按 `consistency.md` 的七条硬约束还原：数值同源、不出现裸值、结构不顺手优化、文案一字不改、状态齐平、换算表固定、动效三处不漏做。
4. HTML 里定稿的值回填进 `02视觉风格/design-spec.md`，以规范为准。
5. 交付时补三行一致性说明（一致到什么程度 / 哪些是允许差异 / 有没有偏离并回改），见 `consistency.md` 第五节。

**HTML 稿 ≠ 验收。** 它验的是"观感对不对"，验不了"真机上会不会裁切、点击区够不够大、低端安卓掉不掉帧"。所以代码写出来还要按主流程验证。

## 八、存量项目里的用法

已经在跑的小程序，加功能前要不要出稿，看波及面：

| 改动 | 出不出 | 走法 |
|---|---|---|
| 新增一个页面，或跨 2 页以上的新流程 | **出** | 只画新页面 + 被改动的现有页面，不重画整个产品 |
| 动到 2 个以上现有页面的结构/信息层级 | **出** | 画出改动后的那几屏，和改动前并排对比 |
| 只在某一页加一块内容 | 不出 | 直接按现有页面加，做完截图看 |
| 改文案 / 按钮名 / 颜色 / 间距 / 删点名元素 | 不出 | 直接改代码 |

存量项目出稿时，**稿子里必须用现有项目的颜色和组件样式**，不要顺手"美化"一下——那会变成一次没人要求的改版，用户看到的是"我的小程序被换了皮"。

## 九、常见错误

| 错误 | 后果 | 改法 |
|---|---|---|
| 一上手就写小程序代码 | 用代码试错，返工按页数翻倍 | 先出 HTML 稿 |
| 稿子里自己发明颜色 | 代码和规范对不上，多一套要清理的值 | 只用 token |
| 只画成功态 | 空/加载/出错上线才发现没设计 | 四态一起摆 |
| 一次画 12 屏全套 | 用户看不完，确认变成走过场 | 只做这轮要拍板的几屏 |
| 把 HTML 的 CSS 直接搬进工程 | 多一套要维护的样式 | 对照重写，见 `prototype-to-code.md` |
| 用户提改动，跳过稿子直接改代码 | 视觉和代码反复对不上 | 先改稿 |
| 拿 HTML 稿当验收依据 | 真机问题一个都没发现 | 稿子只验观感，落地还要验证 |
| 存量项目出稿时顺手重设计 | 用户觉得产品被换了皮 | 只用现有值 |
